# ISS26 v0.9.5 — Stage 6: происхождение флага Боснии в стадионной графике

**Статус:** проведён независимый аудит текущей Test 06 и стабильной v0.9.4. Созданы диагностика 34 стадионных GDC, анализатор VRAM PCSX-Redux и 8 тестов. **Новой игровой сборки пока нет:** для прямой модификации GDC источники сжатия ещё не подтверждены. Play Game остаётся 0.9.4, Test Game остаётся 0.9.6-teamidentity-test06.

## Подтверждено

- Исследован именно загруженный пользователем оригинальный EU Track 01 (SHA256 `D9B483BDEA7774346DF437FEBF038E68CB2C4AD9932A7AD993D3C2B1F620EA44`) с полным независимым патчем Test06 (SHA256 `3A2B98ECFDAA693F8C652543F9A7122D6095EC488C757268D67970688714A636`) и отдельным сравнением со стабильной v0.9.4.
- Найдены команды загрузки GPU, перекрывающие исходную область Боснии (style10, VRAM x864, y320, размер 16×28 слов) в **34 из 34** стадионных `GDC_*`.
- У всех 34 стадионных файлов команды пишут **32×128 слов** в область VRAM `(x=864, y=256)`, то есть затрагивают не только Боснию, но и соседнюю графику.
- У 33 из 34 GDC указатель этой команды выходит за размер файла **при предполагаемой** базе загрузки 0x800C0000. Это не доказывает реальный адрес, но опровергает упрощённую гипотезу прямого файлового указателя для большинства ресурсов.
- Нулевая успешность пробного поиска прямого WE-потока в этих командах (0 из 34). Не значит, что потока нет: вероятна дополнительная распаковка/адресация в оперативной памяти; нельзя угадывать исходный offset.
- **Все 34** `GDC_*` в стабильной v0.9.4 уже заметно отличаются от чистого оригинала (в совокупности более двух миллионов изменённых байтов); **в Test06 они полностью совпадают с v0.9.4**. Поэтому применяйте доработки на восстановленную именно v0.9.4 + Test06 с оригинальными SHA-предусловиями, а не прямо поверх чистого GDC из 2001 года.
- VRAM-снимки PCSX-Redux `.vram` размером 2,097,152 байта в существующем архиве содержат пригодный для анализа первый 1,048,576-байтовый слой 1024×512×16-bit. Дополнительный слой не следует трактовать как видеопамять.
- Пробный запуск на **СТАРОМ** архиве VRAM показал несоответствие подготовленному рисунку (0/896 совпадающих байт в конкретном снимке), что ожидаемо для другой сборки и **ничего не доказывает о Test06**.

## Инструменты

`stage6_gdc_pointer_audit.py`: безопасно индексирует 34 GDC, проверяет GPU-команды, исходные объёмы, совпадение с v0.9.4 и возможные WE-потоки. Не модифицирует бинарные данные.

`stage6_vram_bosnia_verify.py`: побайтно сравнивает VRAM-плитку x864/y320 (16 слов × 28 строк = 896 байт) с подготовленной текстурой Боснии. Принимает `.vram` файл размером 1 или 2 МБ либо ZIP и точное имя файла внутри. **Для валидации нужна запись актуального Test06**, сделанная после загрузки флага в меню и после загрузки стадиона. Даже совпадение VRAM не доказывает, что на экране выбрана нужная палитра CLUT.

`test_stage6_*`: восемь модульных тестов: позиция VRAM, точная длина, GPU пересечение, безопасные отрицательные случаи, корректная WE-декомпрессия на синтетическом потоке.

### Пример

```bash
python stage6_gdc_pointer_audit.py --track "ORIGINAL_Track01.bin" --patch "ISS26_Test06.iss26p" --baseline "ISS26_0.9.4_preview.iss26p" --inventory stage6_gdc_extent_eu.txt --out stage6_results
python stage6_vram_bosnia_verify.py --vram "test06_prematch.vram"
python -m unittest -v test_stage6_gdc_pointer_audit test_stage6_vram_bosnia_verify
```

## Следующий технический шаг

1. Получить одновременные GPU/VRAM-снимки **именно Test06** (выбор Боснии → загрузка стадиона → HUD), сопоставить их с expected tile и палитрой.
2. Выявить в эмуляторе фактический источник RAM-указателей `GDC_*`, установить decompress/load pipeline вместо предположений о 64-КБ базе.
3. После этого сделать точечную 4bpp-замену **ровно одной** плитки в каждом реально задействованном потоке. Валидация декодирования, EDC/ECC, исходного SHA и тест в эмуляторе обязательны.
4. Отдельно идентифицировать источник кода названия команды в предматчевом экране и 24×8 флага у счёта; нельзя массово заменять старые трёхбуквенные коды, так как они могут быть системными идентификаторами.
